# Deployment Assets

This directory holds the Docker Compose and immutable BOM assets for
**PID-02 — Immutable Graylog DEV Stack**.

Rules:
- no floating image tags;
- exact image digests recorded (`BOM.md`);
- no secrets committed;
- environment-specific values external (`.env`, gitignored — see
  `.env.example`);
- persistent volumes explicit (named Docker volumes, not bind mounts);
- DEV and PROD configuration separated (this PID is DEV only; PROD is a
  later, separately governed PID).

## Files

| File | Purpose |
|---|---|
| `docker-compose.yml` | The three-service FALCON Graylog DEV stack (`graylog-falcon`, `datanode-falcon`, `mongodb-falcon`) on `falcon-net`. Compose project name `falcon`. |
| `BOM.md` | Exact immutable image tags + SHA-256 digests, compatibility evidence. |
| `.env.example` | Git-tracked, non-secret template. Every variable the compose file requires, with placeholder values and an explanation. |
| `.env` | Real runtime config + secrets. **Not Git-tracked.** Generated by `bootstrap.sh`. |
| `bootstrap.sh` | Idempotent generator: creates `.env` from `.env.example` with fresh random secrets if one does not already exist. `--force` regenerates — but refuses against an already-initialized `mongodb-falcon` (MongoDB never re-applies its root password to existing data; see the script's header comment) unless also given `--i-know-this-requires-a-data-wipe-or-manual-mongo-rotation`. |
| `reset-dev.sh` | Deliberate DEV-reset: tears down and recreates the stack, wiping only FALCON-named volumes. Requires an explicit confirmation flag. `--dry-run` to preview. |
| `content-packs/falcon-baseline-v1.json` | Exported Graylog Content Pack: FALCON stream + saved search (dashboard included for reference — see the known Graylog 7.1.9 limitation noted below). Re-installable via the Graylog REST API (`/api/system/catalog`, `/api/system/content_packs`) for reproducibility. |

## Quick start

```bash
cd deploy
./bootstrap.sh                       # generates ./.env with fresh secrets (prints root password once)
docker compose -p falcon up -d       # bring the stack up
docker compose -p falcon ps          # check health
```

Graylog GUI/REST API: `http://192.168.11.10:9010/` (bound explicitly to the
dell-debian LAN IP, never `0.0.0.0`). Login as `admin` with the password
`bootstrap.sh` printed when it generated `.env`.

## Isolation from the unrelated Project IRIS Graylog stack

This host also runs a separate, unrelated Graylog stack (Project IRIS /
tradingReport): containers `graylog` / `graylog-mongo` /
`graylog-elasticsearch`, network `graylog_default`, host ports `9000` /
`12201`, compose directory `/srv/graylog`. FALCON's stack never touches,
joins, restarts, reconfigures or reuses anything from it. Every FALCON
Docker resource carries the `-falcon` suffix (`FF-CONTAINER-01`,
`docs/architecture/03-CONTAINER-NAMING.md`) and lives on its own
`falcon-net` network and its own named volumes, so `docker ps` /
`docker network ls` / `docker volume ls` make the separation visually
obvious.

## Timezone doctrine (FF-GUI-TIME-01)

Canonical FalconEvent timestamps — storage, APIs, correlation, machine
processing — are UTC always, everywhere, no exceptions. Only the Graylog
**GUI**, for human operators, renders timestamps in `Europe/London`
(GMT in winter, BST in summer, standard IANA DST behaviour). This is set
via `GRAYLOG_ROOT_TIMEZONE=Europe/London` (sourced from
`FALCON_GRAYLOG_ROOT_TIMEZONE` in `.env`) for the root/admin account.

Empirically verified against this running 7.1.9 instance (see the PID-02
delivery report for the full winter/summer proof): the root user's
display timezone is controlled by the server-side `root_timezone`
setting (`GRAYLOG_ROOT_TIMEZONE` env var) — it cannot be changed from the
GUI, only by changing the environment variable and restarting the
`graylog-falcon` container. Every **other** (non-root) Graylog user has
their own independent, GUI-editable timezone preference under
`System > Users > <username> > Settings > Time zone`, which defaults to
Graylog's `UTC` fallback if never set, and does NOT inherit
`root_timezone`. Every future FALCON operator account must be created
with, or have set immediately after creation, `Europe/London` as its
own profile timezone — this does not happen automatically.

## Synthetic test-only Graylog input — NOT canonical FALCON ingress

For this PID only, a GELF HTTP input is configured on `graylog-falcon`,
bound to `127.0.0.1` **inside that container's own network namespace only**
(no `ports:` mapping to the host, no exposure on `falcon-net`, no LAN
exposure). It exists solely to prove that a FalconEvent-shaped fixture,
flattened to GELF, can be ingested, indexed by Data Node, and found via
search/API/GUI. It is reached only via `docker exec graylog-falcon curl
127.0.0.1:<port>/gelf`.

This input:
- is **not** the canonical FALCON ingress contract (that is PID-03's job);
- must never be reused by real producers (HERMES/ARES/HELIOS/TRON);
- should be disabled/removed after PID-02 acceptance if that can be done
  cleanly (see the PID-02 delivery report for whether it was left in
  place or removed, and why).

> **Gotcha:** creating a non-global (`"global": false`) input via
> `POST /api/system/inputs` silently never launches unless `"node":
> "<node-id>"` is also supplied in the create request body — there is no
> obvious error, it just sits created-but-not-running, which looks like a
> connection-refused when you then try to reach it.

The flattened GELF message shape used for this test is a test convenience
only — it is not the FalconEvent envelope, and must not be treated as one.

**Status:** the test input was removed from the running instance after
testing completed (`DELETE /api/system/inputs/<id>`), confirmed via
`GET /api/system/inputs` returning zero inputs. It is not present in any
committed file (it was created/deleted purely via the live REST API, not
via compose or content pack), so there is nothing left to clean up in
Git.

## Known limitation: Content Packs cannot carry Views-based Dashboards in Graylog 7.1.9

Confirmed empirically while building `falcon-baseline-v1.json`: exporting
a Views-based Dashboard through `POST /api/system/catalog` (resolve) and
feeding the result into `POST /api/system/content_packs/{id}/{rev}/installations`
fails server-side with `Cannot construct instance of
org.graylog2.contentpacks.model.entities.DashboardEntity, problem: Null
widgets` — the catalog/export path serialises widgets nested under
`data.state.<queryId>.widgets`, but the content-pack install-time
`DashboardEntity` deserialiser still expects the pre-Views, flat
`data.widgets` shape. **Streams and Views of type `SEARCH` round-trip
correctly** (proven: deleted the live stream + saved search, reinstalled
them from this exact content pack file, got back the same title, stream
rule and widget field list). The `DASHBOARD` entity in the file is kept
for documentation/reference and may work once Graylog fixes this, but do
not rely on it reinstalling automatically. Also confirmed: a Stream's
`index_set_id` is **not** preserved across a content-pack round trip
either (it installs against whatever index set is default at install
time) — re-point it to `FALCON Evidence` manually after installing, or
change the target system's default index set first.

> **Gotcha:** `POST /api/system/content_packs/{id}/{rev}/installations`
> requires the body wrapped as `{"entity": {"parameters": {}, "comment":
> "..."}}` — a bare `{"parameters": {}, "comment": "..."}` body 400s with
> a confusing `entity cannot be null` error.
